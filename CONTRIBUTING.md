# Contributing to PayloadLens

Thanks for considering a contribution. PayloadLens is a small, focused
project by design — please read this before opening a large pull request,
so we can agree on direction before you invest a lot of time.

## Ground rules

- Be respectful and constructive. See [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).
- No real customer data, no proprietary code, and no production payloads in
  issues, pull requests, demo fixtures, or the exported demo application —
  ever. Use synthetic examples with `example.com` / `example.test` domains,
  the same way the existing [`demo/`](demo) content does.
- Security reports do not belong in public issues — see
  [SECURITY.md](SECURITY.md).

## Getting set up

```sh
git clone https://github.com/B2DEV-TECH/apex-payload-lens.git
cd apex-payload-lens
npm install
npm test
```

Requirements: Node.js 20+ to run the JavaScript test suite and the build,
and an Oracle APEX 26.1+ workspace if you want to install and exercise the
plugin end-to-end (not required just to run the tests).

## Project layout

See [docs/architecture.md](docs/architecture.md) for the full picture. In
short:

- `src/js/payload-lens.js` and `src/css/payload-lens.css` — the hand-written
  client library. `dist/` holds the built, minified copies
  (`npm run build`); never edit `dist/` by hand.
- `plugin/payload_lens_pkg.sql` — the hand-written PL/SQL render package.
- `plugin/region_type_plugin_b2devtech_payload_lens.sql` — the APEX plugin
  export: attributes, help text, render callback, and the embedded copy of
  `dist/`. Generated by APEX, not written by hand — see
  [Changing the APEX plugin definition](#changing-the-apex-plugin-definition).
- `demo/payloadlens_demo_app.sql` — the demo application export (also
  generated by APEX); `demo/*.json` — synthetic fixtures.
- `scripts/build.mjs` — esbuild bundling. `scripts/sync-plugin-files.mjs` —
  re-embeds `dist/` into both exports (`npm run sync:plugin-files`) and
  checks them for drift (`npm run check:plugin-files`).
- `tests/` — the Vitest suite. `docs/` — documentation.

## Making a change

1. Open an issue first for anything beyond a small fix — a bug report, or a
   short proposal for a new feature — so we can discuss the approach before
   code is written. This is especially true for anything touching masking
   or rendering, given their security role (see
   [docs/security.md](docs/security.md)).
2. Create a branch off `main` for your change.
3. Keep `src/js/payload-lens.js` dependency-free and free of `innerHTML`,
   `eval`, or `new Function(...)` — this is a hard architectural
   constraint, not a style preference. See
   [docs/security.md](docs/security.md#how-rendering-avoids-xss-no-innerhtml-ever).
4. Add or update tests under `tests/` for any behavior change. A change to
   masking rules, parsing/empty-state classification, or rendering safety
   should come with a test that would fail without your fix.
5. Run the tests, the build, and the sync before opening a pull request:

   ```sh
   npm test
   npm run build
   npm run sync:plugin-files    # re-embeds dist/ into the plugin/ and demo/ exports
   npm run check:plugin-files   # what CI runs; must report "in sync with dist/"
   ```

   Commit the regenerated `plugin/*.sql` and `demo/*.sql` together with the
   `src/` change — CI fails when the embedded files differ from `dist/`.
6. Update the relevant doc under `docs/` if your change affects configured
   behavior, the JavaScript API, or the security model. Add an entry under
   **Unreleased** in [CHANGELOG.md](CHANGELOG.md).

## Changing the APEX plugin definition

The plugin export in `plugin/` is the unmodified output of APEX's own
export, so attributes, help text, and the render callback name are changed
in APEX and re-exported, not edited in the file:

1. Install the current export into a development application on APEX 26.1
   (see [docs/installation.md](docs/installation.md)) and make the change
   under **Shared Components → Plug-ins → PayloadLens**.
2. Re-export it with SQLcl, connected as the parsing schema:

   ```text
   sql -S your_schema/your_password@your_connect_string
   SQL> apex export -applicationid <app id> -expComponents "PLUGIN:<plugin id>"
   ```

   `<plugin id>` is the `plugin_id` of `B2DEVTECH.PAYLOAD_LENS` in the
   `apex_appl_plugins` view. Replace
   `plugin/region_type_plugin_b2devtech_payload_lens.sql` with the generated
   file, then run `npm run sync:plugin-files` so the embedded JavaScript and
   CSS are the ones built from `dist/`, whatever the development
   application had installed.
3. PL/SQL changes go to `plugin/payload_lens_pkg.sql` (hand-written);
   reinstall it with `@plugin/payload_lens_pkg.sql`. If the render function
   starts reading a new attribute, keep the `attribute_NN` numbering in step
   with the plugin definition.
4. The demo application is re-exported the same way when it needs to
   change: `apex export -applicationid <demo app id> -expOriginalIds` →
   `demo/payloadlens_demo_app.sql`, then `npm run sync:plugin-files`.

Two things to keep in mind: an export carries the exporting instance's
version stamp (`p_release`), and APEX refuses to import a file from a newer
release — so export from the oldest release the project supports (26.1
today), never from a newer one. And both exports must stay entirely
synthetic: no workspace users, no real hostnames, `example.com` only.

## Pull requests

- Keep pull requests focused on one change. Large, mixed-purpose PRs are
  harder to review and more likely to be asked to split up.
- Describe *why* the change is needed, not just what it does — link the
  issue it addresses where applicable.
- CI (test suite, build, and the embedded plugin files check) must pass
  before a PR can be merged.

## Reporting bugs / requesting features

Please use the issue templates provided in this repository — they ask for
the information needed to reproduce a bug or evaluate a feature request
efficiently.
